## 二、docx → MDX 的可复用流程

下一篇番外照这个顺序走。**每一步都先验证再动手**，因为一旦批量替换错了，混在 4500 字里根本看不出来。

### 1. 拆 docx（它就是个 zip）

```
解压 → word/document.xml   正文与段落属性
       word/media/*.png    嵌入的图
       word/_rels/         图与锚点的对应关系
```

要注意的 OOXML 细节，踩过的：

- `w:ind w:firstLineChars="200"` = 首行缩进 2 字，是**段落属性**而不是正文里的空格。所以"段首已经有空格了"这句要区分两种情况：真空格（要删）和 Word 的缩进属性（本来就不该进 MDX，缩进由 CSS 的 `--read-indent` 给）。
- `<w:txbxContent>` 里**嵌套 `<w:p>`**。用非贪婪正则抓段落会被文本框里的段落串味，抓之前先把 txbxContent 剔掉。
- 图有两种锚定：`wp:anchor`（浮动，可拖）与 `wp:inline`（随文）。这篇 5 张全是 anchor。
- 单位：EMU ÷ 9525 = px，twips ÷ 20 = pt。`wpg:wgp` 组合图形的子项坐标在 `a:off` / `a:ext`。

### 2. 先统计，再替换

三件事**都是先证明安全才做的**，不是直接跑正则：

| 处理 | 怎么先证明它安全 |
|---|---|
| 121 个 `＂`(U+FF02) → `“ ”` | 数出来 124 个引号标记、**偶数**，交替替换后无异常；重点验了跨段引用 `[17]→[23]`（格里亚那段，[17] 开引号，[18]–[22] 是内层单引号的独白，[23] 才闭合）——交替法在这种嵌套下仍然对得上 |
| 删 11 处半角空格 | 全文**零个 ASCII 字母**，所以半角空格不承担分词职责，11 处全是标点填充 |
| 直接进 MDX 不转义 | 扫了 `< > * _ [ ` { \| & \` 与行首的列表/标题/引用记号，**全部为 0**（唯一命中的是我自己插的 `<empty>` 占位符） |

> `＂`(U+FF02, 全角引号) 这个字符是 Word 输入法的产物，它**不区分左右**，所以不能靠字符本身判断开闭，只能靠出现次序交替。这也是为什么必须先确认总数是偶数。

用户选了弯引号，选的时候看过预览、知道代价：

> 引号 = `“ ”` 弯引号

（代价是行首的开引号左侧有半个字宽的空白，视觉缩进看着像 2.5 字而不是 2 字。这是纸书也有的现象，`text-spacing-trim: space-first` 只处理行首标点的**挤压**，不会把引号拉到顶格。实测对话段首行左偏移 = 精确的 2em（桌面 36px / 手机 34px），也就是说排版起点是对的，剩下的是字形本身的侧边距。）

### 3. frontmatter

```yaml
---
slug: qingming
title: 清明
date: "2024.4"      # ⚠️ 引号必须有
wordCount: 2906
status: published
---
```

⚠️ **`date` 的引号是硬要求**：裸写 `2024.4` 会被 YAML 解析成**数字** 2024.4，而 `readBaseMeta` 要的是 string，类型对不上。`2023.1-2023.7` 那种带连字符的反而安全（自然是字符串）——所以这个坑只在"看起来像小数"的日期上出现，最容易漏。

`wordCount: 2906` 的口径是**不含空白的字符总数**（汉字 2472 + 中文标点 253 + 弯引号与省略号 175 + 拉丁 6），与 Word 的「字符数(不计空格)」和网文站的字数口径一致。纯汉字数是 2472。**口径是 agent 定的**，想改成纯汉字数就换 2472。

## 三、关键决策

### 决策 1：`SLUG_RE` 按域拆成两个，而不是放宽成一个

主线是 `01-mist`（带序号），番外是 `qingming`（不带）。原来只有一个 `/^\d{2,}-[a-z0-9-]+$/`，番外过不了。

```ts
const SLUG_SHAPE: Record<ContentDir, RegExp> = {
  chapters: /^\d{2,}-[a-z0-9-]+$/,
  extras: /^[a-z][a-z0-9-]*$/,   // 首字符限字母：挡住 `01-…` 这种伪序号
};
```

**为什么不合并成一个宽松的 `/^[a-z0-9-]+$/`**：那样主线文件名**漏了序号也能过**，而漏序号的后果是 `listSlugs` 的 `.sort()` 静默失效——它依赖"文件名字典序 = 章序"这个前提。排出来的顺序还挺像对的，属于最难查的那类错。

**为什么番外的正则要限制首字符是字母**：番外顺序的唯一真源是 `EXTRA_DATA` 的数组顺序（理由在 `extras.ts` 顶部）。文件名一旦带数字前缀，那个数字就成了第二个顺序真源，与 `EXTRA_DATA` 一漂就是静默错序。

连带把 `listSlugs` 的文档改了：它的"升序"对主线**是章序**，对番外**只是字母序**——番外那边排序的唯一用途是让 `generateStaticParams` 的输出稳定。

### 决策 2：`Story.target` 从 `slug` 派生，不手填

`Story` 加了 `slug?: string`，`target` 由工厂算：

```ts
const extra = ({ slug, ...rest }: Omit<Story, "target">): Story => ({
  ...rest, slug, target: slug ? `/extras/${slug}` : "#",
});
```

- **不复用 `id` 当 slug**：现有 id 里有大写和空格（`"new year"`、`"Qingming"`），过不了 slug 正则；而 id 已经被时间轴/轮盘当 React key 用，改它牵动那边。
- **`slug` 缺省 = 正文还没进仓库**（7 篇里目前只有《清明》有）。缺省时 `target` 是 `"#"`，轮盘照旧渲染、只是点不动。
- ⚠️ **`EXTRA_DATA.slug` 与 `content/extras/*.mdx` 的对齐仍然没有构建期校验**（08-06 log 就记着这条）。这边写 `qingming` 而文件叫 `qing-ming.mdx`，结果是一个 404 链接，构建不报错。校验器还没写，见 §七。

### 决策 3：番外薄壳与章节薄壳**刻意重复**，不抽公共组件

两者眼下只差 header 里一行元信息。但它们的差异会越长越大（番外没有上下篇、没有章序号、将来可能有专属装帧），过早合并的代价是**每加一处差异就往里塞一个 boolean prop**。等到差异稳定了再抽。

番外**共用** `.chapter-page` / `.chapter-prose`，没有另起 `.extra-*` 一套——排版契约只该有一份。

顺带一个显示上的差异：

```tsx
<p className="chapter-meta">番外 · {meta.date}</p>
```

⚠️ 番外**显示 date**，而主线章节页刻意不显示（上一篇 log 的决策 9），不是漏了：主线有两个时间（`storyYear` 世界内 / `date` 写作日期），摆出来要先想清楚给读者看哪个；番外只有 `date` 一个时间，而且它就是藏书阁轮盘上的标识，页面上不给会对不上。「番外 ·」这个前缀和整行的存在都是 **agent 定的**。

### 决策 4：装帧件写在**正文文件里**，不做成番外通用组件

用户的判断：

> 这个不是每个番外都有的，是这篇特有的。然后你说做成 term，我觉得是个不错的建议，但是我还是希望它能在文末出现。这组装帧件有点像本文的赞助商这样。

所以定位是**本篇的赞助商/协力名单**：华东（政府）+ 书部（机构）+ 老禾奶茶（商家）+ 阿米尼报社（出品方）。既然只有《清明》有，就写在 `qingming.mdx` 里，不进外壳层也不进 `mdx-components.tsx`。

⚠️ 用户同时说 Term 是"不错的建议"，但 **Term 不能替代文末出现**。两件事：文末名单（已做）＋ 行内点名弹卡（待做，§七）。

用裸 `<img>` 而不是 `next/image`：`public/` 路径拿不到自动尺寸，而这几张是小体积透明 PNG（5~30KB），转 WebP 的收益抵不上多一层 loader。与 `mdx-components.tsx` 里对章节插图的同一判断一致。`width`/`height` 写死是为了防 CLS，取的是 **docx 里 `wp:anchor` 的显示尺寸**（不是 PNG 像素尺寸），这样保留作者手摆的相对大小关系。

### 决策 5：不复现 Word 里的出血排版

从 `wp:anchor` 坐标还原了作者的摆法，发现两件事：

1. **四张下层图是按底线对齐摆的** —— 底边分别在 321 / 322 / 318 / 321px。这是整个 §8 里**唯一有原稿依据**的设计值，直接变成 `align-items: flex-end`。
2. **那一行总宽 668px，而正文栏只有 553px** —— 作者是让它**压过左右两边页边距**的。

第 2 点**没有复现**。网页上做出血只能靠负 margin，而负 margin 在 600~800px 这段视口会把内容顶出屏幕（正文宽随视口收，负值不收）。拿一整类断点 bug，换一个读者只会看成"排版没对齐"而不是"故意压边"的效果，不值。

按 AGENTS.md，视觉参数归用户。这一节的数值**除了 `align-items: flex-end`** 全是 agent 定的：

| 值 | 定成什么 | 改大改小会怎样 |
|---|---|---|
| `.chapter-colophon` `margin-top` | `7em` | 比 `hr` 的 3.5em 大一倍。这里**没有分隔线**，全靠空白说话——调小了装帧件会像正文的一部分 |

| 横排 `gap` | `2.4rem 2rem` | 行距 2.4 / 列距 2。列距小于行距是为了让"同一行是一组"更明显 |

## 五、实测发现（三个，其中一个是真 bug）

自查方法同上一篇：CDP + Node 20 `--experimental-websocket`，零依赖。视口 1440×900 / 768×900 / 700×900 / 390×844。

### 1. 真 bug：`body` 的纸色一直没生效（我上一轮埋的）

实测 `body` 背景是 `rgba(0, 0, 0, 0)`。

```scss
.chapter-page { --read-paper: #faf7ef; }   // §1
body:has(.chapter-page) { background: var(--read-paper); }   // ← 失败
```

**`body` 是 `.chapter-page` 的祖先，而自定义属性只向下继承。** 祖先取不到后代定义的变量，`var()` 解析失败，然后 `background` 回退成 `initial`（transparent）——**不是**回退成某个合理值。实测印证：`--read-paper` 在 `.chapter-page` 和它的后代上都读得到，在 `html` / `body` 上是未定义。

Windows 上**一点症状都没有**（没有橡皮筋滚动），只在 iOS / macOS 过度滚动时露出一条全站冷白。上一轮就是这么漏掉的。

**修法**：用编译期变量把真源收成一个。

```scss
$paper: #faf7ef;                                   // 单一真源
.chapter-page { --read-paper: #{$paper}; }         // ⚠️ 必须插值
body:has(.chapter-page) { background: $paper; }    // 普通属性，直接写
```

- ⚠️ 自定义属性里**必须写 `#{$paper}`**：Sass 把 `--x: …` 的值当纯 CSS token 流，不做变量替换，写 `$paper` 会把 `"$paper"` 这四个字符原样输出给浏览器然后静默失效。普通属性反而直接写就行。
- **为什么不把 §1 整节提到 `:root:has(.chapter-page)`**（那样 body 也能读到变量）：等于把**整份排版**押在 `:has()` 上——不支持时字号、行宽、缩进一起没。现在这个写法即使 `:has()` 不支持，丢的也只是回弹条的颜色。
- 修完实测 `body` = `rgb(250, 247, 239)`，与 `.chapter-page` 一致，且变量仍然只在 `.chapter-page` 作用域内（§1 "不写进 `:root`" 的意图没破）。

### 2. 探针 bug（不是布局 bug）：`rowLines` 一直报 4

我用"不同的 `y` 值有几个"来数折了几行，结果 4 个视口都报 4 行。**是探针错的**：`align-items: flex-end` 让高度不同的图有不同的 `top`。真相在 `bottom`——桌面四张全是 5533（一行），手机 6845/6845/6939/6939（两行，即 2×2）。

**教训与上一篇同一条**：量之前先想清楚"这个数真的能代表我要判断的事吗"。

### 3. 截图伪影（不是颜色 bug）：正文看着是蓝灰带棕

`deviceScaleFactor: 1` 的 Windows 截图里，宋体正文看起来偏蓝偏棕，而标题是纯黑——差异大到像是 `--read-ink` 没生效。**量了才知道是对的**：`p` 和 `.chapter-title` 的 computed `color` 都是 `rgb(38, 34, 32)`。那层彩色是**子像素抗锯齿**：宋体细笔画只有 1px 宽，彩边占满整个笔画；标题笔画粗，彩边占比小所以看着纯黑。真机上人眼看不出来。

### 4. 顺手发现：正文滚过 Nav 时两层文字叠在一起

桌面截图里正文末行直接压在 `World | Codex | Characters` 上，两层字互相糊掉。Nav 是 `fixed` 且背景透明，而**阅读区是全站唯一会长时间滚动的页面**，所以只有这里会撞。

这正好回答了上一篇 log §八 里悬着的那个问题——"长文阅读时顶栏要不要随滚动隐退"。现在有实证了：**不是"要不要"的品味问题，是撞了**。属外壳层改动（`NavMode.scroll` 加第三种姿态，或给 Nav 加毛玻璃底），没动。
