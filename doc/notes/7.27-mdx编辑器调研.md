# 2026-07-27 MDX 写作编辑器调研：结论是做,但做成「写作器 + 导出器」

> 本文是调研结论 + 任务交接说明。接手的 agent 读完这一篇即可开工,不需要回溯原始对话。
> 状态:方案已定,**代码尚未开始**。仓库尚未创建。

## 一、背景

### the-a 项目侧的现状

`doc/decisions/tech-stack.md` 已拍板「内容载体 = MDX」:小说章节、世界观词条、设定笔记一律用 MDX 撰写、随代码进 Git,早期 <100 篇用 MDX 直管。`doc/decisions/asset-organization.md` 进一步定了章节插图放 `public/chapters/<slug>/`,写作时用纯字符串路径引用(不 import)。

但**代码层面 MDX 完全未落地**(2026-07-27 核实):

- `package.json` 无任何 MDX 相关依赖(`@next/mdx` / `@mdx-js/*` / `remark-*` / `rehype-*` 全无)
- 全仓库 `.mdx` 文件数 = 0
- `next.config.ts` 是空壳 `NextConfig = {}`,无 MDX 配置
- 无 `mdx-components.tsx`
- `app/_experiences/` 下只有 `home/v1/`

也就是说:**MDX 管道、章节路由、章节排版样式、内容组件清单(`<Dialogue>` 之类)都还不存在。**

### 用户的实际痛点

用户目前的写作流程是「在别的软件里码字 → 复制到目标格式」(类比:Word 写完复制进 md)。他要的不是「编辑仓库里已有的 .mdx 文件」,而是**一个能直接码文、码完导出成可用 MDX 的写作工具**。

参照物是 **Typora**:内联所见即所得,加上一个能看源码的状态。

### 决定性需求:字词级 trigger

用户要求**正文里某些字词能作为 trigger 触发效果**。经确认是两类:

1. **悬停弹出词条卡片** —— 指向一个世界观词条
2. **视觉 / 气氛效果** —— 发光、低语感之类,不指向任何词条

这条需求是整个技术选型的锚点:它必须在正文里标出"是哪几个字",**推不到 CSS 层**,所以内容天生需要行内 JSX。凡是不支持行内 JSX 的方案一概不可用。

用户所说的「批注」就是词条卡的一种用法,**不需要独立的批注组件**。

### 已评估并排除的方案(别再提议)

| 方案 | 排除原因 |
|---|---|
| **脚本化替代编辑器**(`pnpm new:chapter` + txt→mdx 转换脚本) | 调研初期的建议,基于对需求的误解——它解决「批量转录既有文本」,而用户要解决「日常码字的场所」 |
| **表单式 Git-based CMS**(Keystatic / TinaCMS) | **用户已实测**:schema 表单 + 富文本框的手感无法承担长篇写作。这类工具适合填文档站的 frontmatter,不适合一口气码几千字 |
| **现成桌面 Markdown 编辑器**(Typora / hellomdx 等) | 写作体验成熟,但**不认行内 JSX**,`<Term>雾港</Term>` 在里面就是裸标签。注意 hellomdx.com 的产品品牌名叫「MDX」但处理的是 `.md`,不是 MDX |
| **MDXEditor**(`@mdxeditor/editor`) | 是**组件库不是应用**,仍需自己做壳/存储/自动保存,只替代内核那一块。且基于 Lexical(CJK 生态更浅)、851 kB gzipped、有已记录的 inline 渲染问题——而行内标记恰是本项目的核心需求,不能在这里冒险 |

> 一条已作废的早期建议:调研中曾提出「尽量别在 MDX 正文里塞 JSX,把变化推到渲染侧」。**字词级 trigger 需求确认后此建议作废**——正文必须承载行内标记。

## 二、已确认的核心决策

| # | 决策 | 理由 |
|---|------|------|
| 1 | 做成**独立仓库的独立桌面工具**,与 the-a 无代码耦合 | 工具与作品解耦,以后写别的东西也能用。用户明确否决了「在线写作」——写作工具的启动成本必须接近零,浏览器标签页做不到 |
| 2 | **真源 = ProseMirror 文档 JSON;MDX 是导出产物,单向,只出不进** | 用户已明确接受。类比其原有的 Word→md 全量覆盖流程:永远在编辑器里改,重新导出全量覆盖 |
| 3 | 源码视图**只读** | 可编辑源码 = 需要 MDX→富文本反向解析器 = 整个项目最贵最易出 bug 的部件,收益仅「偶尔想手改源码」。MVP 锁死只读 |
| 4 | **编辑区即预览区**,不做左右分栏 | Typora 的精髓不是预览窗口,而是打字的区域本身就已排版好。只需给编辑区套上真实章节排版 CSS |
| 5 | 富文本内核用 **Tiptap(ProseMirror 系)**,不用 Lexical、不自研 contenteditable | 决定性理由是中文输入法:ProseMirror 十年来在 CJK composition 上踩平的坑,别的方案要重踩一遍。附带好处是 Markdown input rules 现成(打 `**粗` 自动变粗体),正是 Typora 手感的本体 |
| 6 | MDX 导出器**自己写**,不用社区 markdown 序列化包 | 输出目标是 MDX 不是 Markdown:要处理 `{`/`<` 转义、`<br />` 自闭合、frontmatter 生成、自定义组件映射成 JSX。就是个遍历 JSON 输出字符串的纯函数,好写好测,不值得为省半天引一个不合身的包 |
| 7 | **先做本地 web 版,验证手感后才套 Tauri 2 壳** | 前端是同一套 React 代码,套壳是最后一步。别一上来就跟 Rust 工具链和代码签名较劲 |
| 8 | 桌面壳选 **Tauri 2** 而非 Electron | 写作工具要「点开就能写」:Tauri 包体几 MB、启动快、内存低,Electron 空壳就 100MB+。Rust 基本不用写,只需装 toolchain |
| 9 | frontmatter 用 **YAML(`---` 包裹)+ remark 插件**,不用 `export const meta = {}` | 见下方专节。核心是目录页要能「不编译就读元数据」 |
| 10 | 内容组件只有**两个行内 mark**(`Term` / `Fx`),插图用纯 Markdown,无批注组件 | 见第 6.5 节。清单精简是因为「批注」被确认为词条卡的一种用法 |
| 11 | 这两个组件实现为 ProseMirror **mark**,不是 inline node | 见 6.5。语义是「一段文字 + 参数」,与内置 `Link` 同构,**工程量远低于 inline node** |
| 12 | **编辑器只打标记,不实现效果** | 编辑器负责「选中'雾港'→ 标为 `Term id=…`→ 显示成高亮」;效果长什么样全在 the-a 渲染侧。代价:编辑区能预览排版,**不能预览交互效果**(须在 the-a dev server 里看) |

### 决策 9 详解:为什么 YAML frontmatter

MDX 的本质是一个 JS 模块,而 `---` 在 Markdown 语法里是分隔线,所以 **MDX 不原生支持 frontmatter**,两条路:

- **A. YAML + remark 插件**:保持 `---\ntitle: …\n---` 的通用形状,额外装插件(一个让解析器别把 `---` 当分隔线,一个把 YAML 转成模块导出)
- **B. `export const meta = {}`**:MDX 原生能力,零插件

**已定 A**,三个理由:

1. **目录页要批量读元数据,YAML 可以「不编译就读」**(决定性理由)。小说必然有按 `chapter` 排序的目录页。A 方案用 YAML 解析器读每个文件头几行即可,一个循环扫完 content 目录,不碰 MDX 编译器;B 方案元数据藏在 JS 里,**必须真的编译并 import 每一个 MDX 文件**才能拿到,一百章就是编译一百个组件只为读一百个标题。
2. **可移植**。`tech-stack.md` 自己写了「量大后再评估 Payload/Sanity 等 CMS」。YAML frontmatter 是 Obsidian / Astro / Hugo / 几乎所有 CMS 都认的通用格式;`export const meta` 是 MDX 专属,迁移要逐篇重写。
3. **导出器更安全**。生成 YAML 就是拼几行字符串;生成 JS 对象字面量要处理引号转义(标题含 `'` 或 `"` 就炸),白增加一类 bug。

B 的真正优势是能写表达式和 import —— 但章节元数据全是静态字符串和数字,用不上。

具体装哪两个插件、怎么在 Next 16 里配,属于 the-a 集成 MDX 时的事(查 `node_modules/next/dist/docs/`,别凭记忆写)。**对编辑器而言,定了 A 就足够开工:导出器照 YAML 拼头部即可。**

### 决策 2 的代价(已知并接受)

手动改过的 `.mdx` 文件,下次导出会被覆盖。MDX 是只出不进的发布产物。用户已确认可接受。

## 三、MDX 本身的坑(用户此前无 MDX 经验,这些由工具负责兜住)

这些坑是**导出器的职责**,目标是让用户码文时永远不需要知道它们存在:

1. **`{` 和 `<` 在 `.mdx` 里是活的语法字符**。中文正文里 `<` 少见,但 `{` 一出现就是解析错误。导出时必须转义。
2. **裸 HTML 在 MDX 里按 JSX 解析**。`<br>` 必须写 `<br />`,`class` 必须写 `className`。
3. **frontmatter 不是 MDX 原生能力**,`---` 会被当成分隔线,需 remark 插件才能认出来。**已定用 YAML 方案(见决策 9)**,导出器照 YAML 拼头部。
4. **`next build` 时编译**。几百章会拖慢构建,<100 篇无感。
5. **中文首行缩进走 CSS `text-indent`,不要在正文里打空格**。选错了后面几百章要批量返工。导出的 MDX 里不应含缩进空格。

## 四、真正的难点:码文体验(不是 MDX)

自建写作工具的风险不在格式转换,而在**手感要打得过用户现在用的软件**。按优先级:

### 1. 丢稿保护 —— 第一优先级功能,不是 nice-to-have

- 输入 debounce 500ms 落盘当前 JSON
- 每 5 分钟写一个带时间戳的快照文件
- 崩溃/刷新后自动恢复
- (web 阶段若用浏览器存储,必须 IndexedDB,**不能用 localStorage**:5MB 上限且同步阻塞)

### 2. IME × input rules —— 最容易翻车的技术点

打拼音期间(composition 未结束)**绝不能触发 Markdown input rules**。ProseMirror 暴露了 composing 状态,但 **Tiptap 默认的 input rules 不会自动帮你规避**,需要显式在 composition 期间禁用。

不处理的症状:打字打到一半,字被莫名替换。

### 3. 撤销/重做

一次 IME 组合输入应该是一次 undo,不是逐字。这也是选成熟框架而非自研的理由之一——自研 undo 栈在 IME 下几乎必然出错。

### 4. 字数统计按**字符数**,不是 word count

中文没空格,`split(/\s+/)` 会把整章算成一个词。

### 5. 明确不做:Typora 的「光标进入粗体时显示 `**` 符号」

那是 Typora 打磨多年的 decoration 逻辑,MVP 做它性价比极低,且容易和 IME 打架。

## 五、技术栈与目录结构

```
自写导出器                       PM JSON → MDX 字符串,纯函数
File System Access API          阶段一:浏览器直读写本地文件(Chromium 系,Safari 不支持)
Tauri 2                         阶段二:套壳成桌面 app
```

> 装依赖前先查 lockfile,不假设任何包已存在。版本号看 registry 实际情况,不凭记忆写。
> **包管理器只用 pnpm。**

```
src/
  editor/          Tiptap 配置、extensions、input rules、IME 处理
  export/          mdx-serializer.ts + 单元测试(这块必须有测试)
  storage/         草稿读写、自动保存、时间戳快照
  ui/              工具栏、章节列表、源码面板
  styles/
    editor-ui.css       ← 工具栏、侧栏、按钮:编辑器自己的皮
    chapter-theme.css   ← 章节正文排版:唯一一份,以后和 the-a 对齐
drafts/            本地草稿库(JSON),gitignore
```

### 两条结构上的硬要求

**`export/` 必须有单元测试。** 转义漏一个 `{`,后果是 the-a 那边 `next build` 失败。纯函数,测试成本极低,没有理由不写。

**样式必须切成两份(`editor-ui.css` / `chapter-theme.css`),不能混。** 这是独立仓库的一个已知代价:编辑区要长得像最终页面,就需要 the-a 的章节排版样式,而两个仓库不会自动同步。

现在 the-a 的章节页还不存在,所以这事无需解决,但**架构上必须留好位置**——以后 `chapter-theme.css` 就是那份要人工与 the-a 保持一致的东西(或抽成小包两边引)。混在一起就再也摘不出来。

## 六、导出格式约定

```yaml
---
title: 第三章·雨夜
slug: 03-rainy-night      # 手填,不从中文标题自动生成
chapter: 3
date: "2026-07-27"        # ⚠️ 必须加引号,见下方 08-06 追加节
wordCount: 3412
status: draft
draftId: <uuid>           # 指回草稿库,便于追溯
# 以下是【世界内时间】—— 2026-08-06 新增,仅主线章节有,见下方追加节
storyYear: 1247
storyMonth: 3             # 可省
storyApprox: true         # 可省 —— 时间不确定
branch: true              # 可省 —— 支线
---
```

### 追加（2026-08-06）：主线新增世界内时间字段，且主线与番外分目录

the-a 侧的 MDX 管道已落地（见 [`logs/2026-08-06-reading-mdx-pipeline.md`](../logs/2026-08-06-reading-mdx-pipeline.md)），实作时契约有三处变化，**导出器要跟着改**：

**1. 主线章节新增四个字段，`storyYear` 是必填。**

`/library` 的横向时间轴（Timeline）已裁定**数据源就是章节 frontmatter**，而它需要的是「故事发生在什么时候」——这和原有的 `date`（现实的写作/发布日期）是两回事，不能复用。

| 字段 | 必填 | 用途 |
|---|---|---|
| `storyYear` | **是** | 世界内时间的年份。Timeline 靠 `ym(storyYear, storyMonth)` 算横向位置，缺了节点无法定位 |
| `storyMonth` | 否 | 世界内时间的月份，省略时按 1 月算 |
| `storyApprox` | 否 | 时间不确定 → 轴上圈与引线转虚线、日期前缀「约」 |
| `branch` | 否 | 支线 → 节点挂轴下方 |

⚠️ **别让写作者手拼 `storyAt: 1247.25` 这种小数年**。the-a 的 `time.ts` 明确警告过：11 月拼出的 `.11` 在数值上小于 9 月的 `.9`，只要出现两位数月份，节点顺序必然排错。导出年和月两个整数就好，换算是渲染侧的事。

**2. 主线与番外分成两个目录，番外没有世界内时间。**

```
content/
├── chapters/<slug>.mdx    主线 —— 有 chapter + storyYear
└── extras/<slug>.mdx      番外 —— 只有 title / date / wordCount / status / draftId
```

分目录的理由：序号不打架（主线第 3 章与番外第 3 篇都能叫 `chapter: 3`）、上下篇导航不串台、frontmatter 形状本就不同（番外「在世界内时间上没有正当位置」）。

**番外不要导出 `chapter` 或任何序号字段** —— 番外的顺序真源是 the-a 侧手写的 `app/_data/library/data.ts`，正文文件里再放一个序号就是第二个真源。长番外拆分同理：拆成并列的多个独立文件（标题写「（上）/（中）」），**不做层级、不加 `series` 字段**。

**3. `date` 必须加引号。**

YAML 会把裸的 `date: 2026-07-27` 解析成 **Date 对象**而不是字符串，而本项目 `date` 的语义是「给人看的串，随便写什么都行」（"约 2029 年冬"、"2023.1-2023.7" 都合法）。the-a 侧已做 Date 兜底（转 `YYYY-MM-DD`），但那会**静默丢掉写作者本来想要的格式**。导出器请一律加引号。

`slug` **手填**:自动拼音转换的结果用户不会满意,且 slug 同时决定 URL(`/chapters/<slug>`)和插图目录名(`public/chapters/<slug>/`),必须稳定。

### slug 命名形状(2026-07-27 已裁定)

形状是 **`<序号>-<描述词>`,全小写短横线,不加任何前缀** —— 例如 `01-mist`、`03-rainy-night`。

背景:此前 `decisions/architecture.md` 的 URL 示例是 `/chapters/01-mist`,而 `decisions/asset-organization.md` 的插图目录示例是 `public/chapters/ch-01-mist/`,多一个 `ch-` 前缀。用户裁定**以 URL 形状为准**(URL 是对外契约),`asset-organization.md` 已对齐并追加变更日志。

对编辑器的影响:

- slug 由写作者**手填**,导出器不自动生成
- 可以加正则校验防手填出错:`/^\d{2,}-[a-z0-9-]+$/`
- **插图目录名 = slug**,两者永远一致,所以编辑器若将来做插图管理,直接用 slug 拼 `public/chapters/<slug>/` 即可

## 六点五、内容组件:两个行内 mark

```mdx
她走进<Term id="mist-harbor">雾港</Term>的时候,雨已经下了很久。
那声音<Fx type="whisper">像是从很远的地方来的</Fx>。
```

| 组件 | 属性 | 用途 | 指向词条? |
|---|---|---|---|
| `Term` | `id` | 悬停弹出世界观词条卡片(用户所说的「批注」) | 是 |
| `Fx` | `type`(枚举:`glow` / `whisper` / `shake` …) | 视觉气氛效果 | 否 |

**插图不需要自定义组件**:纯 Markdown `![](/chapters/<slug>/pier.jpg)` 即可,路径约定见 [`decisions/asset-organization.md`](../decisions/asset-organization.md)。将来若要控制布局(全宽 / 并排)再加块级组件。

`Fx` 的 type 列表在编辑器里配成一个**可扩展数组**;每种 type 具体长什么样属于 the-a 渲染侧,编辑器不关心。

### 为什么是 mark 而不是 inline node(关键)

`<Term id="x">雾港</Term>` 的语义是「这段文字带一个标记 + 参数」,与 ProseMirror 内置的 `Link`(包裹文字 + `href`)**结构完全同构**。按 mark 实现的收益:

| | mark | inline node |
|---|---|---|
| 参照实现 | Tiptap 内置 `Link`,几乎照搬 | 从零设计 |
| 光标进出边界语义 | 不存在此问题 | 每种情况手写 |
| IME 在其中输入 | 成熟路径(等同在加粗文字里打字) | bug 温床 |
| 跨越它的选区 | 天然支持 | 需专门处理 |

> 调研中途曾把它当 inline node 评估并判定为「富文本编辑器里最难的一类」,该判断已作废。按 mark 实现难度大幅降低。

### 导出器的两个中文专属坑

**1. 标签周围不能有多余空格。** `她走进 <Term>雾港</Term>` 会在中文之间渲染出一个空格。中文排版无词间空格,导出时必须紧贴。英文项目遇不到,中文项目必踩。

**2. mark 嵌套顺序必须固定。** 一个词若既是 `Term` 又加粗,`**<Term>雾港</Term>**` 与 `<Term>**雾港**</Term>` 都合法但渲染结构不同。**约定:JSX 在外、Markdown 语法在内。** 否则同样的编辑操作会导出不同结果。

两条都归 `export/` 的单元测试覆盖。

### 词条 id 的校验

`Term` 的 `id` 必须指向真实存在的词条。

- **MVP**:手填,不校验
- **导出时**收集全部 `Term` 的 id 到一份清单(可写进 frontmatter 或旁路文件),方便在 the-a 侧写脚本查死链
- **后续**:编辑器读 the-a 的词条目录做自动补全 + 失效引用高亮
